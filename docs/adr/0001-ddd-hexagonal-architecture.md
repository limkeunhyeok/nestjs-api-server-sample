# 0001 - 핵심 도메인에 대한 DDD 및 포트-어댑터 아키텍처 도입

## 상태 (Status)

제안됨 (Proposed) / 승인됨 (Accepted)

## 배경 (Context)

현재 시스템은 NestJS의 전형적인 Modular 구조를 따르고 있으며, 서비스 계층이 TypeORM 영속성 모듈에 강력하게 결합해 있습니다. 이로 인해 다음과 같은 문제점이 관찰되었습니다:

1. **빈약한 도메인 모델 (Anemic Domain Model)**: 데이터베이스 스키마와 직접 매핑되는 엔티티(`PostEntity` 등)는 단순한 데이터 바구니 역할만 수행하며, 핵심 비즈니스 규칙과 검증 절차가 서비스 계층에 절차지향적으로 구현되어 있습니다.
2. **기술 스택에 대한 과도한 의존성**: 비즈니스 정책을 처리하는 서비스 계층이 TypeORM 및 데이터베이스 세부 구현체에 직접 의존하여, 향후 프레임워크나 ORM 라이브러리를 변경하거나 업그레이드할 때 비즈니스 코드 전반을 수정해야 하는 리스크가 존재합니다.
3. **유스케이스 모호성**: 단일 서비스 클래스가 조회, 생성, 수정, 삭제 등의 비즈니스 유스케이스를 모두 관리하여 SRP(단일 책임 원칙) 위반 우려가 있고 클래스의 크기가 지속적으로 비대해집니다.

## 결정 (Decision)

비즈니스 코어를 격리하고 변경에 강한 안정적인 애플리케이션 구조를 확립하기 위해 **도메인 주도 설계(DDD) 및 포트-어댑터(Hexagonal) 아키텍처**를 핵심 모듈(예: `posts`)에 시범 도입하기로 결정합니다.

구체적인 설계 원칙은 다음과 같습니다:

1. **도메인 순수성 보장 (Domain Purity)**:
   - `domain/` 폴더 내의 도메인 모델(`Post`, `Comment` 등)은 외부 프레임워크 라이브러리(NestJS, TypeORM 등)에 절대 의존하지 않는 순수 TypeScript 클래스로 작성합니다.
   - 비즈니스 상태 변화와 검증 정책은 도메인 모델 내부의 풍부한 행위 메서드(Rich Domain Method)로 구현합니다.
2. **포트-어댑터 패턴**:
   - 도메인과 유스케이스는 인프라 데이터베이스에 직접 접근하지 않고, `domain/repository-ports/`에 정의된 포트 인터페이스를 사용해 통신합니다.
   - 인프라 레이어(`infrastructure/database/`)에서 이 포트 인터페이스를 실제로 상속/구현하는 레포지토리 어댑터(`PostRepositoryAdapter`)를 작성하고, 영속성 엔티티(`PostOrmEntity`)와의 데이터 변환은 정적 매퍼(`PostMapper`)를 활용해 책임을 완전히 격리합니다.
3. **CQS(명령 조회 분리) 패턴**:
   - 기존의 단일 서비스를 명령(Command) 유스케이스와 조회(Query) 유스케이스로 나누어 독립된 클래스로 구현합니다.
   - Command 유스케이스에는 트랜잭션 관리를 강제하여 데이터 원자성을 보장하고, Query 유스케이스에는 읽기 최적화 및 적절한 캐싱 전략을 유연하게 적용합니다.
4. **프레임워크 예외의 전면 배제 (Zero Framework Exception Dependency)**:
   - 예외 흐름 수준에서도 프레임워크 기술 독립성을 극대화하기 위해, 프로젝트 전반에서 NestJS가 제공하는 `HttpException` 계열의 임포트 및 상속을 엄격히 배제합니다.
   - 모든 비즈니스 도메인 오류는 순수 TypeScript 클래스인 `BaseDomainException`으로, API 레벨 오류는 `ApiException`으로 일원화하여 던집니다.

## 결과 (Consequences)

### 장점 (Pros)

- **유지보수 용이성**: 데이터베이스 기술이나 외부 API 스택이 변경되더라도 비즈니스 도메인의 핵심 로직은 무영향으로 보존됩니다.
- **테스트 용이성**: 순수 TypeScript로 구성된 도메인 모델과 유스케이스는 데이터베이스 커넥션이나 복잡한 모킹 모듈 없이도 단위 테스트(Unit Test)를 손쉽게 작성할 수 있습니다.
- **코드 가독성**: 유스케이스 단위로 클래스가 세분화되어 개별 비즈니스 행위의 책임 범위와 구현 코드가 명확해집니다.

### 단점 (Cons)

- **보일러플레이트 코드 증가**: 도메인 엔티티, ORM 엔티티, 매퍼, 유스케이스, 포트, 어댑터 등 기존 구조 대비 생성해야 할 파일 수가 늘어납니다.
- **학습 곡선**: 프레임워크가 제공하는 기본 모듈 스타일 대비 고수준의 아키텍처적 이해도가 요구됩니다.
- **예외 변환 수동 매핑 공수**: 프레임워크 기본 예외 메커니즘을 사용하지 않으므로, 커스텀 예외와 HTTP 상태 코드 간의 정교한 매핑 테이블을 전역 필터에서 직접 관리해야 하는 유지보수 공수가 수반됩니다.
