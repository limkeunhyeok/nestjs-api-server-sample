# 0003. 기술적 공통 인프라 모듈의 구조 표준 및 배치 규정

## 맥락과 문제 정의 (Context and Problem Statement)

본 프로젝트는 비즈니스 도메인의 중요성에 따라 순수 도메인을 격리하는 DDD(도메인 주도 설계) 및 Hexagonal(포트-어댑터) 아키텍처를 규정하고 있습니다. 그러나 비즈니스 기능이 아닌 외부 기술 연동(예: JWT 서명/검증, 파일 스토리지, 로깅 등)을 전담하는 공통 기술 모듈들이 `src/modules/` 하위에 다른 핵심 도메인 모듈(users, posts 등)과 동등한 수준으로 섞여 배치되어 아키텍처의 도메인 정체성에 혼선을 유발하고 있습니다. 또한 이러한 기술 지향 모듈에 강제로 DDD 다층 계층을 적용하는 것은 불필요한 코드 비대화와 오버엔지니어링을 초래합니다. 이들을 어떻게 관리하고 배치해야 할까요?

## 의사결정 동기 (Decision Drivers)

* **비즈니스 도메인 모듈의 가독성 향상**: `src/modules/` 하위에는 순수 비즈니스 상태 변화가 발생하는 Bounded Context 모듈만 남겨 아키텍처 정체성을 공고히 함.
* **불필요한 보일러플레이트 코드 제거**: 기술 연동을 위한 Wrapping 모듈 개발 시 불필요한 계층화(Domain Entity, Application, Mapper 등)를 배제해 효율을 극대화함.
* **유지보수 비용 감소 및 응집도 향상**: 단일 기술 라이브러리를 Wrapping하는 컴포넌트는 단일 디렉토리에 플랫하게 모아 높은 응집도를 갖도록 함.

## 검토한 대안들 (Considered Options)

* **대안 1**: 기술 모듈에 대해서도 강제적으로 DDD 및 Hexagonal 아키텍처 계층 구조를 전면 강제 적용함.
* **대안 2**: 기술 모듈에 대해 DDD 계층 구조를 배제하되, 모듈 위치는 `src/modules/`에 그대로 유지하여 플랫 구조로 작성함.
* **대안 3**: 기술 모듈에 대해 DDD 계층을 적용하지 않는 플랫 구조를 준수하며, 위치를 `src/common/` 하위로 이전해 비즈니스 모듈과 구조적으로 분리함 (선택).

## 결정 내용 및 결과 (Decision Outcome)

선택한 안: **대안 3**
이유: 비즈니스 도메인(src/modules/)과 단순 기술 유틸리티(src/common/)를 명확히 디렉토리 수준에서 격리할 수 있으며, 기술 모듈 내부의 불필요한 계층화를 막아 오버엔지니어링 문제를 완벽히 차단할 수 있기 때문입니다.

### 기대 효과 및 영향 (Consequences)

* **장점**:
  - `src/modules/`에는 오직 핵심 도메인 비즈니스 모듈만 정갈하게 남아 프로젝트 아키텍처 지향점을 명확히 보여줍니다.
  - `jose-jwt` 등 공통 프레임워크 기술에 연계된 모듈들은 `src/common/<module-name>/` 디렉토리에 간단한 Flat 구조(Module, Service, Interface, Const 등)로 구성되어 개발 및 유지보수가 단순화됩니다.
* **장점**:
  - `jose-jwt` 등 공통 프레임워크 기술에 연계된 모듈들은 `src/common/<module-name>/` 디렉토리에 간단한 Flat 구조(Module, Service, Interface, Const 등)로 구성되어 개발 및 유지보수가 단순화됩니다.
* **단점**:
  - 기존에 `src/modules/`를 참조하던 모듈의 임포트 경로를 `src/common/` 하위로 마이그레이션해야 하는 1회성 변경 비용이 존재합니다.

### 구현 검증 계획 (Confirmation)

* 기술적 인프라 모듈(예: `jose-jwt`) 내부 디렉토리에 `domain/`, `application/`, `infrastructure/` 와 같은 다층 서브디렉토리가 없으며, 단일 폴더 하위에 핵심 서비스와 모듈 파일이 평평하게 정의되어 있는지 검사합니다.
* `src/modules/` 폴더 하위에 비즈니스 도메인 명세를 갖추지 않은 순수 기술 컴포넌트 폴더가 잔존해 있는지 아키텍처 코드 리뷰 과정에서 체크합니다.

## 대안별 장단점 세부 비교 (Pros and Cons of the Options)

### 대안 1 (DDD 전면 강제 적용)

* **장점**: 모든 모듈의 하위 폴더 구조가 동일하게 유지되어 기계적인 일관성을 가질 수 있음.
* **단점**: 비즈니스 도메인이 존재하지 않는 단순 Wrapping 모듈(예: JWT, Logger)에 도메인 엔티티, 영속성 엔티티, Mapper 등을 억지로 구성하면서 보일러플레이트 코드가 증가하여 개발 속도를 현저히 늦춤.

### 대안 2 (Flat 구조를 취하되 src/modules/ 유지)

* **장점**: 디렉토리 이전 비용이 없고, 임포트 경로를 수정할 필요가 없음.
* **단점**: `src/modules/` 폴더 하위에 어떤 폴더는 DDD 계층을 따르고, 어떤 폴더는 Flat한 형태를 띠게 되어 아키텍처 정합성이 불명확해지고 가독성이 저하됨.
