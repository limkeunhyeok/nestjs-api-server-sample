# 기능 및 API 명세 (Specifications)

이 디렉토리는 프로젝트에서 제공하거나 제공 예정인 개별 비즈니스 요구사항, 인터페이스, 그리고 백엔드 API 설계 사양서를 수집하고 명세하는 공간입니다.

---

## 스펙 작성 규칙

* **바운디드 컨텍스트/기능별 개별 파일 작성**:
  - 대형 기능 단위 또는 비즈니스 도메인(Bounded Context)마다 하나의 독립적인 파일로 분리하여 작성하며, 파일명은 `kebab-case.md` 방식을 사용합니다.
* **필수 프론트매터(Front-matter) 기재**:
  - 작성 현황과 책임자를 명확히 추적하기 위해, 모든 스펙 문서의 최상단에는 반드시 아래의 YAML 프론트매터를 선언해야 합니다:
  ```yaml
  ---
  status: draft | review | approved | implemented | deprecated
  owner: <작성자 이름 / GitHub 핸들러>
  last-updated: YYYY-MM-DD
  ---
  ```
  - **status 값의 의미**:
    - `draft`: 사양 구상 및 초안 작성 중인 단계.
    - `review`: 문서 완성을 마친 뒤 구조나 비즈니스 설계 검토를 거치는 단계.
    - `approved`: 구현을 진행해도 좋다고 기술적 합의가 최종 확정된 단계.
    - `implemented`: 실제 구현 및 E2E 테스트 검증이 소스 코드에 최종 반영 완료된 단계.
    - `deprecated`: 레거시 기능이 되어 더 이상 유효하지 않은 스펙으로 분류된 단계.

---

## 권장되는 스펙 구조 (Recommended Sections)

1. **개요 (Summary)**: 1~2개 문장으로 이 기능이 '무엇'이고 '왜' 개발이 필요한지 정의합니다.
2. **목표 및 제외 대상 (Goals / Non-goals)**: 구현할 경계 범위를 명확히 긋습니다. (무엇을 만들고, 무엇을 만들지 않을 것인가)
3. **유즈 케이스 및 유저 스토리 (User stories / Use cases)**: 비즈니스 사용자 혹은 연동 클라이언트가 이 기능으로부터 얻는 구체적인 효용을 서술합니다.
4. **인터페이스 및 API 스펙 (Interface / API)**: 요청/응답 DTO 스키마 명세, 엔드포인트 경로, 외부 API 와의 데이터 포맷 계약을 상세히 기록합니다.
5. **동작 상세 및 에러 핸들링 (Behavior)**: 해피 패스(정상 시나리오)뿐만 아니라, 예외 상황 및 오류 시 던져지는 HTTP 예외 스펙을 정밀하게 다룹니다.
6. **오픈 질문 (Open questions)**: 의사결정을 유보했거나 추가적인 비즈니스 분석이 필요한 열린 사항들을 적어둡니다.

> [!NOTE]
> 설계 내용 중 광범위한 기술 아키텍처나 구조적인 합의(DB 선택, ORM 아키텍처 등)가 필요한 사항은 여기에 상세 기술하지 않고, 반드시 **[ADR](../adr/)**로 분리하여 작성한 뒤 본 사양서 내부에서 참조 링크 형태로 연결해 줍니다.
